## Karpathy のパターンに何を加えたか

Karpathy の gist は最小限のパーツでパターン全体を説明する。下記4つは規模が大きくなった後に遭遇した問題。Karpathy の方法を置き換えるのではなく拡張する。

```
Karpathy:   raw ─→ wiki
本リポ:     raw ─→ atoms（トピックブランチ別に組織）─→ wiki
```

4つの拡張：

**1. アトム層。** Karpathy は raw から wiki へ一段階コンパイル。その間に atoms を挿入。1つのアトム = 1つの主張、frontmatter 付き（ソース、タイプ、深度、タグ、日付）。アトムは真実のソース、wiki は派生キャッシュ。wiki ページの事実が誤っていたら、元の素材ではなくアトムに戻って検証。元の gist のコメント `frosk1` が指摘した「情報損失」と「虚偽の真実のソース」問題を解決。

**2. トピックブランチがアトム層に落ちる。** Karpathy の wiki は扁平。私は原子をテーマ別に repo root の branch フォルダに分類（1ブランチ = 1フォルダ）、扁平な wiki ページにコンパイル、ファイル名にテーマプレフィックス付与（`wiki/<branch>-<subtopic>.md`）。アトム層は参照しやすく、wiki 層は index で位置付けしやすい。

**3. 二層リント。** Karpathy は「矛盾、ゴーストリンク、孤立ページ、陳腐化声明を見つける」をリント操作に混在させる。分割：プログラム層（`scripts/lint.sh`）は確定的チェック処理（ゴーストリンク、孤立ページ、フォーマット違反、時間マーカー）秒単位で完了。LLM 層は意味的チェック処理（矛盾、陳腐化判定）。プログラム層が先に実行、LLM の注意力がフォーマット問題で消費されるのを避ける。

**4. 並行編集の命名ロック。** Karpathy は一度に1ページ書く。N 個のエージェントが並行編集する場合、同じコンテンツセットに異なるファイル名を生成（`mcp-plus-skills.md` vs `mcp-plus-skills-architecture.md`）。解法：ファンアウト前に slug 命名空間をプリロック。エージェントはコンテンツを事前定義済みスロットに入力。命名は非担当。

## フロー実行方法

```
┌─────────┐  インジェスト  ┌────────────┐  コンパイル ┌─────────┐
│  raw/   │ ─────────▶ │ <branch>/  │ ─────────▶ │  wiki/  │
│         │  (LLM      │ atom.md    │  (LLM      │ 扁平    │
│ 素材    │  抽出)     │ atom.md    │  グループ) │ ページ  │
└─────────┘            │ ...        │            └────┬────┘
                       └────────────┘                 │
                                                      │
                                ┌─────────────────────┼─────────────────────┐
                                ▼                     ▼                     ▼
                          gen-index.sh           lint.sh              log-append.sh
                              │                     │                     │
                              ▼                     ▼                     ▼
                          index.md           lint-report.md            log.md
```

Karpathy サイクルとの対応：

```
Karpathy:   raw → wiki → {インジェスト、クエリ、リント}
本リポ:     raw → atoms → wiki → {インジェスト、クエリ、プログラムリント、LLM リント}
```

真の仕事はアトム層で行われる。Wiki はアトムから再構築可能。アトムは wiki から再構築不可。

## このリポジトリに何があるか

```
llm-atomic-wiki/
├── README.md              ← 英文版
├── README.zh-TW.md        ← ここ
├── STORY.md               ← 実装完了の個人ストーリー（英文）
├── METHODOLOGY.md         ← 6段階パイプライン
├── CLAUDE.md              ← LLM 用スキーマ
│
├── raw/                   ← あなたの素材をここに配置（gitignore）
│
├── atoms/                 ← ナレッジアトム、テーマブランチ別に組織（gitignore）
│   ├── README.md
│   ├── _template.md       ← 新アトム作成時にコピー
│   ├── <branch-1>/        ← 1ブランチ = 1フォルダ
│   ├── <branch-2>/        ← 例：ai-agent/、ai-skills/、mcp/...
│   └── ...
│
├── wiki/                  ← コンパイル成果物、扁平（gitignore）
│   └── _template.md       ← 新 wiki ページ作成時にコピー
│
├── index.md               ← 自動生成ナビゲーション（gitignore）
├── log.md                 ← 変更記録、追記式（gitignore）
│
└── scripts/
    ├── lint.sh            ← プログラム層リント
    ├── gen-index.sh       ← wiki/ から index.md 再構築
    ├── log-append.sh      ← log.md に 1 行追記
    └── README.md
```

フレームワークファイル（README、METHODOLOGY、CLAUDE、scripts、各層 _template）はバージョン管理対象。実際のコンテンツ（raw、atoms 内のブランチとアトム、wiki、生成 index/log）は gitignore。意図的かつ核心設計。このリポジトリはキット、データではない。

## クイックスタート

1. **このリポジトリを Fork。**
2. **`METHODOLOGY.md` を読む**—raw から wiki への 6 段階、保守ループ付き。
3. **`CLAUDE.md` を読む**—正式スペック（アトムフォーマット、wiki フォーマット、ブランチルール、操作、禁止事項）。
4. **`.gitignore` を編集**—記載されているブランチ名を自分のものに変更。
5. **素材を `raw/` に配置**—任意のテキストフォーマット。PDF、トランスクリプト、投稿エクスポート、記事。
6. **LLM でパイプラインを駆動**—Claude Code（またはあなたのエージェント）を `CLAUDE.md` に指し、一括インジェストを指示。
7. **毎回コンパイル後、スクリプトを実行：**
   ```bash
   ./scripts/gen-index.sh        # wiki インデックス再構築
   ./scripts/lint.sh             # プログラム層健全性チェック
   ./scripts/log-append.sh "..." # 変更を記録
   ```
8. **毎週または大量インジェスト後に 1 周期 LLM リント 実行**—詳細は `METHODOLOGY.md` 参照。

完全サイクル：`インジェスト → コンパイル → インデックス/ログ → リント → クエリ`。素材が累積するたびに繰り返し実行。

## なぜ価値があるか（そしていつ価値がないか）

Karpathy の論点は、知識は素材から毎回再生成される何かではなく、持続的で複合的なアーティファクトであるべき。Compile が RAG を上回る。同意だが、条件付き：

- **知識量は ~200ページの wiki 以内。** 超過後、index.md スキャン性能が低下、ベクトル検索併用が必要。
- **知識は比較的安定。** 整理しているのは認識マップ、リアルタイムニュースではない。更新頻度は日/週単位、分単位ではない。
- **単一の観点主がいる。** 個人知識整理、100 の作者の意見集約ではない。
- **品質が覆蓋範囲より重要。** 500ページの浅い記事より 50ページの深い記事。

これらの条件を満たさない場合、RAG がより適切。両者は相互排斥ではない。コア知識は Compile で、ロングテールは RAG で。

この gist の本当の洞察はしばしば過小評価される：Karpathy の核心貢献は wiki 品質の良さではなく、**LLM は wiki 保守に飽きない**という点。ほとんどの個人知識システムは構造が悪いから死ぬのではなく、保守コストが高すぎて人が持たない。LLM が保守コストの性質そのものを変える。これが gist が指し示す真のロック解除ポイント。フォーマット詳細より格段に重要。
