# README — llm-atomic-wiki システム概要

## プロジェクト定位

`llm-atomic-wiki` は Andrej Karpathy の [LLM ウィキ](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) パターンに由来する。著者はこのパターンを完全に実装し（584件のソーシャルメディア投稿、8,668件の返信 → 630個の知識アトム、83ページの ウィキ、11個のブランチ）、規模拡大後に限界が露呈した部分に対して4つの拡張を施した。

このリポジトリは**フレームワーク**（方法論、スキーマ、スクリプト、ディレクトリ構造）のみを提供する。著者の実際の内容は含まれない。設計上、フォーク 可能なキットであり、データセットではない。

## Karpathy パターンへの4つの拡張

```
Karpathy:   raw ─→ wiki
本リポ:     raw ─→ atoms（ブランチ別に組織）─→ wiki
```

1. **アトム層**：生 と ウィキ の 間に アトム を 挿入。1つの アトム = 1つの 主張。フロントマター付き（ソース、タイプ、深度、タグ、作成日）。アトムが 真実の ソース、ウィキ は 派生 キャッシュ。ウィキ が 誤っていたら、アトムに 戻って 検証 してから 再編集。元の ギスト で 指摘 されていた「情報 損失」と「虚偽の 真実の ソース」の 問題を 解決。

2. **ブランチ 組織**：アトムは トピック別 に 独立 フォルダ に 整理（1ブランチ = 1フォルダ）。ウィキ は 扁平 に 保つ が、ファイル名 に ブランチ プレフィックス を 付与（`wiki/<branch>-<subtopic>.md`）。アトム層 は 参照 しやすく、ウィキ層 は インデックス で 位置付け しやすい。

3. **二層 リント**：プログラム層（`scripts/lint.sh`）は 決定的 チェック（幽霊 リンク、孤立 ページ、形式 違反、時間 マーカー）を 秒 単位 で 実行。LLM層 は 意味的 チェック（矛盾、陳腐化 声明）を 実行。プログラム層 が 先に 走る ため、LLM の 注意力 を フォーマット 問題 で 浪費 しない。

4. **並行 編集 の 命名 ロック**：複数 の エージェント が 並行 で 編集 する 場合、同じ コンテンツ セット に 異なる ファイル名 が 付与 される。解法：ファンアウト 前に スラグ 名前空間 を 事前ロック。エージェント は 割り当て られた スラグ に コンテンツ を 入力 し、命名 は 行わない。

## 適用範囲（いつ価値があるか）

コンパイル が RAG を 上回る 前提条件：

- 知識量 が 約 200ページ の ウィキ 以内（超過後 は インデックス スキャン 性能 が 低下、ベクトル 検索 を 併用 する 必要あり）
- 知識 が 比較的 安定 している（分 単位 ではなく、日/週 単位 での 更新）
- 単一 の 観点 主（個人 知識 整理。多数 作者 の 意見 集約 ではない）
- 品質 が カバレッジ より 重要（500ページ の 浅い 記事 より 50ページ の 深い 記事）

条件 を 満たさない 場合 は RAG の 方 が 適切。両者 は 相互 排斥 ではない。コア 知識 は コンパイル で、ロングテール は RAG で 処理。

著者 は、この ギスト で 最も 過小評価 されている 洞察 は、Karpathy の 核心 貢献 は ウィキ 品質 にはなく、**LLM は ウィキ 保守 に 飽きない**という 点 だと 考える。ほとんど の 個人 知識 システム は 保守 コスト の 高さ で 死ぬ が、LLM はこの 保守 コスト の 本質 を 根本的 に 変える。

## ワークフロー

`raw/`（素材）→ インジェスト（LLM 抽出）→ `atoms/<branch>/`（アトム）→ コンパイル（LLM グループ化）→ `wiki/`（扁平ページ）、その後3つのスクリプトを実行：

- `gen-index.sh` → `index.md` 再構築（ナビゲーション）
- `lint.sh` → `lint-report.md` 生成（プログラム層 健全性 チェック）
- `log-append.sh` → `log.md` に追記（変更 記録）

完全な ループ：**インジェスト → コンパイル → インデックス/ログ → リント → クエリ**、素材 が 累積 するたびに 繰り返し実行。核心原則：真 の 作業 は アトム層 で 行われる。ウィキ は アトム から 再生成可能 だが、その逆 はできない。

## ディレクトリ構造のポイント

- バージョン管理 対象 の フレームワーク ファイル：`README.md`、`README.zh-TW.md`、`STORY.md`、`METHODOLOGY.md`（6段階 パイプライン）、`CLAUDE.md`（LLM への 正式 スペック）、`scripts/`、各層 の `_template.md`。
- 知識 コンテンツ（`raw/`、`atoms/`、`wiki/`）および 生成 される `index.md`、`log.md` はすべて ギット バージョン管理 対象。ギット 履歴 そのもの が 変更 監査 チェーン。生 の 差分 は ギット で 直接 検出可能（下記 の 生 差分 作業 フロー 参照）。フォーク を 公開 する際 に コンテンツ が 機密 の 場合のみ `.gitignore` で 除外。

## クイックスタート（8ステップ）

1. このリポジトリを フォーク
2. `METHODOLOGY.md` を読む（6段階 パイプライン + 保守 ループ）
3. `CLAUDE.md` `AGENTS.md` を読む（アトム 形式、ウィキ 形式、ブランチ ルール、操作、禁止事項）
4. バージョン管理 範囲 を確認：生 / アトム / ウィキ はデフォルト すべて ギット 対象
5. 素材 を `raw/` に配置（任意 のテキスト形式）
6. LLM（Claude Code など）に `AGENTS.md` を指す 指示 を与えて パイプライン を駆動
7. 毎回 の コンパイル 後に `gen-index.sh`、`lint.sh`、`log-append.sh` を実行
8. 毎週 または 大量 インジェスト 後に LLM リント 1周期 を実行

## 使用手順（日常操作説明）

上記の「クイックスタート」8ステップ完了後、日常運転は5つの操作を中心に進行（正式規範は `CLAUDE.md` 参照）：

### 1. インジェスト（素材ライブラリ → アトム）— 初回使用ステップ

1. **素材を配置**：ソースファイルを `raw/` に配置（任意 の テキスト形式）
2. **インジェスト 指示 を下す**：1文で 3つ の 入力 を指定。例：「`raw/` 下 の XX ファイル に対して インジェスト を実行」
3. **3つ の 入力 を確認**：ソース パス（`raw/` 下 の どのファイル）、ターゲット ブランチ（`atoms/<branch>/`、新規 ブランチ は ユーザー 承認必須）、範囲（全量 vs パイロット。50+ ファイル の 大規模 コーパス は、ユーザー が アトム スタイル を審査 した後 に拡大 する前に、1ブランチ の パイロット 推奨）
4. **範囲内 の ソースファイル を通読**：ファイル に 構造化 ヘッダ（概要、キーワード など）がある 場合 は、まず ロードマップ として使用。大きすぎる ファイル は「構造化 概要 + 本文 サンプリング」で 対応。レポート に 注記 が必要。
5. **セグメント別 に 分類**：`抽出`（保存 価値 のある 主張/規則/原則）、`スキップ`（純粋 参考 データ。テーブル 参照、ID リスト。ソースファイル に 残しておき、アトム化 しない）、`遅延`（曖昧、クロスブランチ、重複 疑い。ユーザー確認 待ち）
6. **アトム を記述**：1アトム = 1主張。独立 した2つ の 主張 は 2つ の アトム に分割。ファイル名 `YYYY-MM-DD-<slug>.md`、フロントマター 規範 に従う。本文 は 冒頭 の 1文 で 核心主張、著者 の 声 を保持。
7. **収尾**：`gen-index.sh` と `log-append.sh` を実行。アトム数、トピック 分布、判断 ポイント、遅延 リスト をユーザー に報告。ユーザーレビュー 後、次 ブランチ または コンパイル へ進行。

（後続の素材が増分更新される場合の差分処理は、下記の「raw 差分作業フロー」参照。初回使用には該当しない。）

### 2. コンパイル（アトム → ウィキ ページ）

- **コンパイル 指示 を下す**：インジェスト 終了後、パイプライン は レビュー 待ち で停止。コンパイル に進む には 個別 指示 が必要。例：「`atoms/<branch>/` 下 の アトム を テーマ別 に コンパイル して ウィキ ページ化」通常 は 範囲 を指定（どの ブランチ）すれば、グループ化 方法 は エージェント が 規範 に従って 判断。
- テーマ別 グループ化 で編集。1ページ 3–8個 の アトム。ファイル名 `<branch>-<topic-slug>.md`。冒頭行 は必ず `# タイトル`。
- クロスリファレンス は `[[wiki-link]]`。時間 制約 のある コンテンツ は 具体的 な 日付 または バージョン 番号。ページ フッタ に ソース アトム ID を列挙。
- 複数 エージェント が 並行 で編集 する 場合、コーディネーター はあらかじめ スラグ リスト をロック。エージェント は コンテンツ を 割り当て られた スラグ に入力 し、命名 は行わない。

### 3. インデックス/ログ（毎 変更後 の 固定 収尾）

アトム または ウィキ に 変更 を加えたら、必ず 実行：

```bash
./scripts/gen-index.sh                    # インデックス再構築
./scripts/log-append.sh "実行内容"         # 変更を記録
```

agent は インジェスト / コンパイル 収尾時に自動実行するため、個別指示は不要。`index.md` または `log.md` が更新されていなければ、「収尾スクリプトを実行してください」と一言促す。

### 4. リント（健全性チェック）

- **リント指示を下す**：プログラム層はコンパイル収尾時に自動実行。LLM 層は個別指示が必要。例：「LLM リント 1周期を実行」毎週または大量インジェスト後の実行を推奨。
- プログラム層：`./scripts/lint.sh` でゴーストリンク、孤立ページ、フォーマット違反、時間マーカーをチェック。出力 `lint-report.md`。エラー報告は修正完了まで完了扱いにしない。
- LLM 層：プログラム層パス後、index + 全 wiki ページを通読。矛盾、概念ギャップ、陳腐化声明、弱い孤立ページを検出。報告の `## LLM Lint` セクションに追記。

### 5. クエリ / ディープクエリ（検索・質問応答）

- **クエリ指示を下す**：agent に直接質問すれば OK。モード指定なしはデフォルト Query。例：「XX のルール」。または明示的に「クエリ：XX のルール」と書いても可。クエリが証拠不足の場合、agent は停止して ディープクエリへの変更を提案するが、自動アップグレードは行わない。
- **ディープクエリ指示を下す**：指示文に「ディープクエリ」の文字を明示してのみ実行。例：「ディープクエリで検証：XX のルール」raw 層の原文に遡る必要があり、証拠チェーン行単位を要求する問題に適す。
- **クエリ**（デフォルト、軽量）：`index.md` + wiki ページ + ページ参照アトムのみ読取。最大 2周期の検索、合計 6ページ。`raw/` 読取禁止、grep など全リポジトリ検索禁止。証拠不足時は停止してユーザーに ディープクエリ変更を提案。自動切替不可。
- **ディープクエリ**（ユーザー明示時のみ実行）：wiki → atom → raw に沿って各主張を追跡検証。最大 5周期の検索、raw は ground truth。最終答には証拠チェーン表（wiki / atom / raw / 検証状態）を添付。

### raw 差分作業フロー（raw ファイル差分発生後の全フロー）

想定エンドツーエンドワークフロー（スクリプト：`scripts/raw-diff.sh` は git 差分・報告、`scripts/ingest-plan.sh` は影響面分析・タスクリスト生成）：

```
           Git リポジトリ
        (Raw / Atom / Wiki)
                 │
                 ▼
          Raw コンテンツ変更
    (追加 / 修正 / 削除 / 名前変更)
                 │
                 ▼
         Git 変更アナライザー
       （Git ファイル変更のみ分析）
                 │
                 ▼
          Raw 差分レポート
        （JSON + Markdown）
                 │
                 ▼
          インジェストプランナー
     （影響受け Atom / Wiki を分析）
                 │
                 ▼
      インジェストタスクリスト生成
                 │
                 ▼
          増分インジェスト
    ┌───────────┬─────┴─────┬───────────┐
    │           │           │           │
    ▼           ▼           ▼           ▼
  追加     修正 /       名前変更   削除
         名前変更+修正   のみ
    │           │           │           │
    ▼           ▼           ▼           ▼
アトム作成  再インジェスト  メタデータ  アーカイブ
         (再生成+差分)  更新
    │           │           │           │
    └───────────┴─────┬─────┴───────────┘
                      ▼
           増分 Wiki 更新
                      │
                      ▼
          アトム / Wiki ファイル更新
                      │
                      ▼
             Git コミット変更
```

各ノードと本リポジトリ既存メカニズムの対応：

| 想定ノード | 対応メカニズム |
|-----------|--------------|
| Raw コンテンツ変更 | ユーザーが `raw/` に追加/編集/ソフト削除（LLM は raw/ 読取専用）。削除は `raw/_archive/` に移動、硬削除は使用しない。アトム層の「永遠に削除するな」哲学に対称。 |
| Git 変更アナライザー | `./scripts/raw-diff.sh`、純 git 差分。`last-ingest` タグをベースラインに、`git diff -M`（リネーム検出内蔵）加未トラッキングファイルスキャン。比較対象は現在の work tree。「raw ファイルで何が起きたか」だけ答え、影響面分析は行わない。 |
| Raw 差分レポート | 差分結果を `raw-diff-report-<日時>` の二重形式で保存：JSON（機械読み取り、インジェストプランナー用）+ Markdown（人間読み）。分類は added / modified / rename-only / rename+modified / soft-deleted。リネーム 2 種は `git diff -M` 相似度で区別（R100 = 純リネーム、R<100 = リネーム+内容変更）。硬削除（ファイル消失かつ `raw/_archive/` にない）は違規。 |
| インジェストプランナー | `./scripts/ingest-plan.sh`、差分レポート（JSON）を読取。atoms の `source_ids` で逆参照して、各変更ファイルが何個の atoms に参照され、それらの atoms が何ページの wiki に編集されているか分析。影響面分析はこのステップで発生し、アナライザーではない。 |
| インジェストタスクリスト生成 | プランナー出力 `ingest-task-list-<日時>.md`：各変更ファイルに 1 タスク（どのブランチに進み、どの atoms / wiki ページに影響するか）。リストは作業キュー。分割消費可。途中中断後は差分 + プランナー再実行で続行可（`last-ingest` タグはそのまま、処理済みファイルは「既 atoms 参照」と注記）。 |
| 追加 → アトム作成 | 通常インジェスト → 新 atoms。 |
| 修正 / リネーム+修正 → 再インジェスト | 主張変化を人手で逐条判断しない：修正ファイルは直接再インジェストして候補 atoms を生成し、既存 atoms と git diff（`created` など生成時刻で変わるフィールドは無視）。差分なし → スキップ、候補破棄、元 atom 保持；差分あり → 新 atom + `superseded_by` + 旧 atom を `_archive/` に。リネーム+修正は先に `source_ids` パス修正、同一フロー。 |
| リネームのみ → メタデータ更新 | git リネーム検出が R100（純リネーム、内容無変更）→ 影響受け atoms の `source_ids` をメタデータレベルパス修正のみ。atom 本文非動作、再インジェスト不実行。 |
| 削除 → アーカイブ | 唯一のパス：ファイルを `raw/_archive/` に移動（ソフト削除）。原文残存、git 履歴完全保持、DeepQuery でも raw 層検証可。atoms はデフォルト保持。内容が廃止確定時のみアーカイブライフサイクル（新 atom / `superseded_by` / `_archive/`）。硬削除操作フロー提供しない。直接削除は差分報告で違規フラグ、復旧要求。 |
| 増分 Wiki 更新 | 影響受け wiki ページのみ再編集（インジェストプランナーの影響面リスト逆参照）。 |
| アトム / Wiki ファイル更新 | 収尾 3 点セット：`gen-index.sh` → `log-append.sh` →（wiki 変更時）`lint.sh`、エラー修正完了まで完了扱いにしない。 |
| Git コミット変更 | 本周期変更をコミット：raw / atoms / wiki 三層をともに `index.md`、`log.md` とともにバージョン管理。1 コミットで「ソース変更 → アトム変更 → wiki 変更」の完全な対応を記録。git 履歴は監査チェーン。コミット後 `git tag -f last-ingest` を実行してタグを本コミットに移動。本バッチ処理完了を宣告。差分ベースラインは `last-ingest` git タグそのもの。スクリプトはベースライン状態を自行管理しない。 |

### 鉄則（してはいけないこと）

アトム作成後は編集不可（旧アトム + `superseded_by` + `_archive/` に移動）。`raw/` に書き込まない。勝手にブランチ作成しない。wiki パッチでアトム層問題を隠さない。ロックなしで並行編集しない。atom または wiki ページを `rm` で削除しない。

- 品質 が カバレッジ より 重要（500ページ の 浅い 記事 より 50ページ の 深い 記事）

著者 は、この ギスト で 最も 過小評価 されている 洞察 は、Karpathy の 核心 貢献 は ウィキ 品質 にはなく、**LLM は ウィキ 保守 に 飽きない**という 点 だと 考える。ほとんど の 個人 知識 システム は 保守 コスト の 高さ で 死ぬ が、LLM はこの 保守 コスト の 本質 を 根本的 に 変える。
